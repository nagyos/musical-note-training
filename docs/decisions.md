# 重要決定事項ログ (Decisions)

このドキュメントは、プロジェクトで「今決めないと後で痛い」要件・技術選定を記録する。

## 原則
- MVP は**オフライン中心・ローカル完結**を最優先。
- Phase 3 (収益化) 以降で初めて「クラウド/バックエンド」が必要になる可能性が高い。
- 決定は「いつまでに」「誰が」「根拠」を残す。

## MVPとは
**MVP (Minimum Viable Product)** = 「ストアに出してユーザーに価値を提供できる最小の製品」。

このプロジェクトの場合（roadmap.md / Phase 1 より）:
- ト音記号中心の音符・休符・記号・強弱・速度の基本識別
- 単語帳（デッキ作成・学習セッション）
- 苦手管理
- 日英対応（UI + 音名切替）
- 最小限の広告
- 完全にオフラインで動く

**含めない（Phase 2以降）**:
- フラッシュカード、リズム練習、和音
- ユーザー作成カード（これがPhase 3の本丸）
- アカウント・クラウド同期（MVPでは不要）

MVPの目的:
- 早くリリースしてフィードバックをもらう
- 開発の方向性を検証する
- 複雑なクラウド/アカウント周りを後回しにする

端末変更時の移行は「MVPでも欲しい機能」として別途扱う（アカウント同期はPhase 3推奨）。

## 2. 詰めておくべき未決定要件 (優先度順)

### A. データ永続化 (Phase 0 で最優先)
**選定**: **Turso (libSQL)** を最初から使用。

**理由（ユーザー意向反映）**
- 「いずれTursoを使うのが見えている」ので、最初からコミットして後で移行する無駄を避ける。
- 開発期間に余裕があり、AI支援で実装コストを吸収できる。
- Tursoのembedded replica機能を使えば、**MVP時もオフライン動作を保ちつつ、将来の同期を自然に追加**できる。
- SQLite互換を維持できるため、データモデル設計が無駄になりにくい。

**アーキテクチャ方針**
- ローカル: embedded replica（ローカルSQLiteファイルとして動作、オフライン優先）。
- クラウド: Tursoサーバーに同期（デバイス間移行・バックアップ用）。
- MVPでは同期を**オフ**またはオプトインにし、完全ローカル体験を提供。
- Phase 3で本格的にアカウント同期を有効化。

**残る決定事項**
- 具体的なFlutter/Dartクライアント（公式libsql client + drift adapterの組み合わせが有力）。
- 同期戦略の細部（フル同期 vs 選択的同期、コンフリクト解決）。
- 認証の導入タイミング（Google AccountをPhase 2〜3で）。

### B. クラウド同期・バックエンドのスコープと端末移行
**新しい方針（2026-06-30 更新）**
- TursoをPhase 0から導入するため、**MVP時点から「オフライン + 将来同期可能な設計」**にする。
- コア体験はMVPでも完全にオフラインで動く（embedded replica）。
- 同期は最初は無効またはオプトインにし、Phase 2〜3で本格有効化。

**端末変更時の移行・引継ぎ**
- 短期（MVP〜Phase 2）: Turso同期をオフにした状態 + JSONエクスポート/インポートでカバー。
- 中長期: Google Account + Turso同期で自動移行。
- Google Accountは「やりたくない」気持ちを尊重しつつ、端末移行のユーザー体験を最も良くできる現実的な選択。
- Emailは二次候補（実装コストが高いため）。

**Phase 3で必要なもの（更新）**
- IAP レシート検証（依然としてサーバー側必須）。
- Turso上のユーザー/デッキデータ + カスタムカードの所有権管理。
- 認証（Google優先）。

**決めないといけないこと（更新）**
- Tursoの具体的な同期モード（embedded replicaの使い方）。
- 認証の導入タイミング（MVPでは任意、Phase 2後半〜3で必須化）。
- プライバシーポリシーで「データはTurso（エッジDB）に保存され、Googleアカウントで同期される」と書けるか。

### C. 認証 (Auth)
MVP: 不要 (アカウントなし)
Phase 3+: 必要になる可能性大

**候補**
- 匿名 + デバイスID (最も簡単)
- Google / Apple Sign In

### D. インフラ / クラウドプロバイダ

#### 現在の状況 (2026-06-30)
- すべてクライアント側 (Riverpod + ローカルDB想定)
- バックエンドは Phase 3 以降で初めて本格検討

#### 比較 (Cloudflare を意識)

| 項目                  | Cloudflare (Workers + D1 + R2) | Firebase | Supabase | コメント |
|-----------------------|--------------------------------|----------|----------|----------|
| IAP検証               | Workers で自前実装            | 公式サンプル豊富 | Edge Functions | どれも可能 |
| DB (ユーザー/デッキ)  | D1 (SQLite)                    | Firestore | Postgres | D1は安いがSQL |
| ファイル/画像保存     | R2 + CDN (激安)                | Storage  | Storage  | Cloudflare強い |
| 無料枠 / コスト       | 非常に安い                     | 寛容     | 良い     | 個人開発向き |
| Flutter統合           | 普通                           | 最高     | 良い     | Firebaseが楽 |
| 開発体験              | Workers (TS/JS)                | Dart/JS  | TS/SQL   | - |
| 将来の拡張 (AI, 通知) | Workers + AI Gateway           | Genkit等 | Edge + AI| - |

**推奨 (現時点)**
- **MVP〜Phase 2**: バックエンド完全不要。ローカルDB (drift推奨) + ファイル資産はGit or assets。
- **Phase 3開始前**に以下を確定:
  1. IAP検証は **Cloudflare Workers** でやる (安くて柔軟)。
  2. ユーザー作成カードの「同期が欲しいか」を決める。
     - 欲しくなければ → Workers (IAPのみ) + ローカル。
     - 欲しいなら → D1 追加 or Firebase フル採用を比較。
- ランディングページや静的アセットが必要になったら **Cloudflare Pages** を第一候補。

**決めないといけないこと (Phase 2 終わりまでに)**
- 「カスタムカードはクラウド同期するのか？」(Yes/No)
- IAP検証をどのプロバイダでやるか (Cloudflare一択でいいか？)
- ユーザーアカウントをどのタイミングで入れるか

## 決めるときの考え方・方針（おすすめ）

### 基本方針
1. **MVPを最速で出す**ことを最優先。クラウドや複雑な認証は後回し。
2. **痛みが出るまで決めない**（例: 実際に機種変更の声が来るまで本格同期は不要）。
3. **PoCで比較する**（1週間以内に動くものを作って体感）。
4. **将来の拡張性を殺さない**（ローカルDBは後で同期しやすいものを選ぶ）。
5. **ユーザー体験 > 開発者の理想**（あなたが「Google Accountはやりたくない」と思っていても、ユーザーが機種変更で困るなら優先）。

### 評価軸（これで候補を比較）
- 開発コスト（今週中にPoCできるか）
- ユーザー体験（移行の簡単さ）
- 保守コスト（長期的に面倒くさくないか）
- プライバシー（データがどこに行くか説明しやすいか）
- 将来性（Phase 3のカスタムカード・IAPと相性が良いか）
- コスト（無料枠でどこまでいけるか）

### 私の現在の最適候補（ユーザー意向反映・2026-06-30更新）

**Phase 0から一貫してTursoを採用**
- **DB**: Turso (libSQL) + embedded replica
  - MVP時: embedded replicaで完全ローカル動作（オフライン優先）。
  - 後から: クラウド同期を有効化してデバイス間移行を実現。
  - メリット: 将来の移行コストゼロ。SQLite感覚を保てる。
- **端末移行**: 
  - まずembedded replica + 任意のJSONエクスポートで対応。
  - Phase 2後半〜3でGoogle Sign-In + Turso同期を有効化。
- **認証**: Google Accountをメインに、Phase 2〜3で導入（匿名フォールバックも検討）。

**Phase 3**
- IAP検証: Cloudflare Workers（または同等）で最小限実装。
- カスタムカード: Turso上にユーザー所有データとして保存 + 同期。
- メール認証: 可能だが優先度は低（Googleで十分カバーできる）。

このアプローチで「最初からTurso」という希望を叶えつつ、MVPのオフライン体験も守れる。

**決め方のステップ（おすすめ）**
1. 今週中に T-004 PoC（driftでローカル + 簡単エクスポート）を作る。
2. 「端末変更で困った」という声が来る or Phase 3設計時に「同期入れるか？」を再判断。
3. 同期を入れる場合は Google Accountを第一、TursoをDB候補として1週間PoC。
4. すべて decisions.md に「決定日・根拠・代替案」を残す。
5. プライバシーポリシー作成時に「データは端末に保存。同期する場合はGoogleアカウントを使用」と明確に書ける状態にする。

これで「決めないといけないこと」を先送りしつつ、ユーザー体験を殺さないバランスが取れます。

### Tursoについて補足（更新）
- 何: libSQLベースのサーバーレスSQLite。**embedded replica** により、ローカルファイルとして高速に動きつつ、オンライン時にクラウドと同期可能。
- なぜ最初から？: ユーザーの意向（いずれ使うなら最初から）と、移行コストを避けたいため。
- MVPでの使い方: embedded replicaをローカル優先で使い、同期は無効/オプトインに。
- Flutter実装のポイント: Turso公式のDartクライアント + 可能ならdrift adapterを組み合わせる。embedded replicaはオフライン体験を損なわない。
- コスト: 個人規模なら無料枠で十分スタート可能。同期量が増えたら有料プラン。
- 欠点と対策: DartサポートはJSほど成熟していない → 早めにPoCして検証。authレイヤーは別途（Google Sign-In）が必要。

- 未マージがコンフリクト要因の可能性はある。`develop` へはマージしてよい。
- `main` へのマージ時のみ PR 承認の段階を踏む。

**決定**

### [2026-07-09] UI / ビジュアル方針（MVP）

**質問**

- **将来**: 背景やテーマを複数用意し、ユーザーが自由に選べるようにしたい。
- **アイコン**: 誰が見ても分かる、よく使われている一般的なデザインにしたい。

**決定**
- **MVP のビジュアル**
  - トーン: 落ち着き・可読性・シンプル（教材 / ツール寄り。装飾過多・キラキラ演出は避ける）。
  - カラー: 落ち着いたニュートラル〜控えめなアクセント（現状の indigo デフォルトは後で調整対象）。
  - コンポーネント: Material 3 の標準パターンをベースに、余白は `AppSpacing` で統一。
  - アイコン: **Material Icons 等の一般的・意味が明確なアイコン**を使う（独自記号や過度な装飾は避ける）。
  - 学習画面: 楽譜と回答 UI を主役に。派手なアニメーションは MVP では入れない。
  - ダークモード: システム追従のまま。ライト / ダークとも落ち着いた配色に揃える。
- **MVP 後（Phase 2 以降）**
  - 設定から **テーマ / 背景プリセットを複数選べる**機能を追加する（配色・背景の組み合わせ）。
- **アプリアイコン・スプラッシュ**（T-170）: 直前までに、一般的で意味が伝わるモチーフ（五線譜・音符など）で検討。

**根拠・補足**
- 全年代向けではコントラスト・タップ領域・意味の分かるアイコンが装飾より重要。
- テーマ切替は設定 UI と `AppTheme` の拡張が必要なため、機能が固まってからの方が手戻りが少ない。

**影響**

- 将来タスク候補: テーマ / 背景プリセット選択（設定画面）
